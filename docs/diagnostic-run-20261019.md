# 同步故障诊断记录

日期：2026-10-19

这次记录用于说明网页“同步”失败的真实原因，避免后续只凭页面提示反复试错。诊断日志采用 JSONL 格式，保存在项目的 `data/diagnostics/` 目录中；日志中的时间使用 UTC。

## 现象

- 直接请求 8000 端口时返回旧的通用错误“同步招聘数据时发生未分类错误”，且没有生成诊断日志。
- 使用当前源码启动的临时后端后，诊断请求能够生成日志，并返回具体失败阶段。
- `boss-cli` 在修复前报错：`Protocol error (Input.dispatchMouseEvent): Invalid parameters ... params.x`。

## 已保存的诊断日志

- `data/diagnostics/sync-20261019T084921.459472Z-73a0ee70.log`
  - 后端执行到 CLI 阶段。
  - CLI 明确记录了 `session-lock-contended` 和 `EPERM`，等待 30 秒后退出。
  - 这次运行说明网页诊断链路已经可以捕获 CLI 的 stderr，而不是把错误压缩成未分类错误。
- `data/diagnostics/sync-20261019T085133.093005Z-e0070a35.log`
  - CLI 在 120 秒超时。
  - 这是超时路径的证据，后续已让超时日志同时保留 CLI 已产生的 stdout/stderr。

## 根因

1. 8000 端口上残留的是旧版本后端。旧版本的健康检查只返回“正常”，启动脚本因此误以为服务可用，网页实际上继续调用旧代码。
2. 旧版 BOSS 侧栏导航把 `page.evaluate` 返回的函数对象当成坐标，得到 `{}`，随后向 Chrome 发送了缺少数值坐标的鼠标事件，于是出现 `params.x - double value expected`。
3. 在隔离运行环境中还观察到 `.boss-cli` 会话锁的 `EPERM` 和 CLI 超时；这类问题现在会写入诊断日志，并显示具体阶段和 stderr。

## 修复验证

- 侧栏导航已改为在页面内找到“职位管理”链接并执行原生 DOM click，不再依赖未解析的坐标对象。
- 使用当前 `boss-cli` 构建直接运行 `positions`，日志显示：
  - `sidebar-search-result {"clicked":true}`
  - 当前 URL 到达 `https://www.zhipin.com/web/chat/job/list`
  - 随后读取到 20 个职位，页面统计为 36 个职位。
- 后端健康版本提升到 `0.2.2`，启动脚本现在必须确认 `/api/health` 返回这个版本；如果 8000 仍被旧进程占用，会明确报告“未启动到当前版本”，不会再静默使用旧服务。
- 网页增加了“调试信息”区域和“诊断同步”按钮。诊断完成或失败后，页面会显示本次诊断日志的绝对路径；调试信息只展示经过筛选的字段，不回显完整 stdout/stderr。

## 下一次启动

关闭当前旧的 AI Recruiter 后，双击项目根目录的 `start-ai-hr.bat`。启动脚本会清理它能识别的旧监听进程，并等待后端健康版本为 `0.2.2` 后才打开网页。进入网页后点击“诊断同步”，页面上的“诊断日志已保存”提示和“调试信息”区域就是本次运行的可核对证据。
